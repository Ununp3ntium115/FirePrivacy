# Original concept coverage

The original main branch contained product and architecture descriptions rather than executable app source. The earlier implementation at `2cc9ba1` supplies additional designs; its adapters were explicitly uncompiled or stubbed. The current branch engineers those ideas with bounded models, real Apple adapters and explicit external gates.

This is a source/integration map. A source implementation, a passing test, an activated device feature and an App Store approval are separate forms of evidence. The full working-source portable workflow passed 240 Core and 111 Python tests. Hosted native run 37394131493 passed both families and unsigned compilation of all three editions at `b9fa051`; later rule/history/KB/legal/UI changes need final native validation. Screenshots remain deferred. See [VALIDATION](VALIDATION.md) for the exact scope, counts and remaining checks.

## Intentional platform boundaries

The app does not enumerate installed apps, read or change other apps’ permissions, disable their SDKs, deep-link their private Settings screens, inspect encrypted traffic, or infer transmission/harm from co-occurrence. Private Cloud Compute has no implemented request path. These boundaries are retained from the original privacy architecture.

The signed rule catalog is implemented as closed data over compiled detectors, with independently recorded versions, source/changelog and reviewed conditions. Its portable configuration/signature/envelope tests and real publisher interoperability pass; final native coordinator tests remain pending. Arbitrary downloaded code, unrestricted condition languages and model-authored findings are outside the design.

The original optional model concept is deliberately constrained to checked presentation selection over deterministic claims rather than unrestricted generated explanations. Original plans for Private Cloud Compute remain disabled and have no request path. iOS 27 URL-reporting APIs are outside this iOS 26 implementation; they must not appear as available consumer features.

## Actual Apple and operator prerequisites

| Requirement | What still needs actual evidence |
| --- | --- |
| Apple account/signing | Active membership/current agreements/roles; enrolled seller identity; registered app/extension/App Group IDs; granted selected capabilities; valid matching certificate/private key/profiles; ASC app record and upload authorization. A team ID or source entitlement is not that evidence. |
| Consumer Safari/DNS | Signed eligible configuration, actual Settings enablement/readback, resolver query/retention/jurisdiction disclosure and truthful failed-removal handling. This consumer edition excludes the separately gated URL/managed providers. |
| URL-filter edition | Real operator PIR/Privacy Pass/OHTTP configuration, matching capabilities/identity and Apple relay validation before non-development distribution, including TestFlight. Compiled provider code does not deploy or approve that service. |
| Managed edition | Actual supported supervised/MDM deployment/operator and granted content-filter capabilities. Local providers do not create an MDM enrollment/control service or prove management eligibility. |
| Maintained signed datasets | Existing operator private key under controlled custody, matching public anchor deployed in app/providers, reviewed source/license basis, live HTTPS envelopes, renewal and sticky revocation operation. The CLI is local preparation, not hosting or operator certification. |
| Optional advisors | Eligible iOS/iPadOS 26 device with ready on-device SystemLanguageModel; or actual user-operated compatible HTTPS endpoint with current exact approval and truthful hosting/retention disclosure. No automatic cloud/PCC service is supplied. |
| Submission information | Matching live policy/support and exact edition metadata, current privacy/age/export/trader/contact/rights answers, final native/device/accessibility evidence and screenshots after validation. On-device analysis alone does not justify a blanket privacy label for optional external operators. |

The detailed current official-source requirements are in [APPLE-REQUIREMENTS](APPLE-REQUIREMENTS.md). These are deployment/submission prerequisites, not unimplemented substitutes for the engineered Core paths. Original repository references to a company do not verify the enrolled seller or rights holder.

A released consumer build must describe its own available services and capability gates accurately. The separate URL/managed editions must not be presented as installed protection merely because their source compiles. No source audit constitutes legal certification or an Apple approval.
